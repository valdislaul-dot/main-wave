# Plan 03-03 — GUI one-key refresh joins the single-flight lock (D-01, ACT-03)

## User-story framing

**As a** user opening the streamlit panel while an API-triggered pipeline is already running, **I want to** click the 🔄 刷新数据 button and be told plainly that the pipeline is already running — with no second run spawning and no corrupted concurrent `data/` write — **so that** the single-flight guarantee of ACT-03/SC2 holds across every entry point on this machine, including the button I click by habit.

<objective>
Apply D-01, the smallest locked change in the phase: `scripts/daily/gui_dashboard.py`'s refresh-button branch (around line 88) gains the shared-lock check — acquire `job_lock.acquire("pipeline", <data/locks under BASE>)` before the existing `subprocess.run` refresh, warn via `st.warning` and skip the run when the lock is held, wrap the run in try/finally so the streamlit `timeout=180` path releases the lock, and warn when a timeout may have left the pipeline running. Everything else in the file stays byte-identical; the import joins the existing top-level `import morning_check as mc` pattern so Win/Mac share the same source (D-03). This is a GUI-side client edit, not an API change — the API's 409-vs-GUI arbitration (03-02) already consumes the same lock file.

Purpose: SC2's "any other entry point" is only real when the GUI actually arbitrates on the same primitive as the API; without D-01, a click during an API job silently double-runs the pipeline against live `data/`. Research Pitfall 7 adds the release-in-finally requirement so the pre-existing `timeout=180` orphan hazard cannot strand the lock.

Output: one modified file, verified by compile, structural source gates, a headless streamlit boot smoke, the full suite, and a manual click-through for the human at end-of-phase.
</objective>

## Flagged Assumptions (spec-less probe fallback — continuation)

- ACT-03 (concurrency probe row, surfaced in 03-01): this plan implements the D-01 GUI side of that row's guarantee on the real client process. [ASSUMED A3] fcntl.flock on macOS behaves equivalently to the probed Windows semantics (advisory, auto-release at process death) — Mac impact is low because Mac runs are serial-by-convention with no crontab lock (D-03) and the GUI is manually operated; the import split keeps Mac bootable, and a Mac-side rollout check is recorded for the 03-03 SUMMARY.
- Probe V4 consequence (verified, not assumed): `subprocess.run(..., timeout=180)` on TimeoutExpired leaves the child alive — so the finally-release plus the may-still-be-running warning are mandatory consequences of D-01, not enhancements; v2 ACT-04 owns the taskkill cleanup.
- The GUI is a trusted local client (single user on the box); its lock usage is advisory cooperation with the API, which remains the authoritative arbiter via its in-memory map + OS lock (Pattern 1 claim order).
