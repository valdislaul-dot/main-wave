# Plan 03-02 — X-API-Key gate + protected trigger/job HTTP surface (ACT-01/ACT-02/ACT-03/SEC-01)

## User-story framing

**As a** consumer of gogo's live operations (cloud panel, scheduled integrator, the user off-machine), **I want to** send `POST /v1/actions/{kind}` and `GET /v1/jobs/{job_id}` carrying my X-API-Key and receive exactly the documented contract — 202 + job_id at once, 409 with the running job_id when a kind is already live (even when the GUI or a manual run holds the machine), terminal job state with a log path when I poll, and 401/403 the moment my key is missing or wrong — **so that** no unauthenticated caller can start a pipeline, no two runs of one kind can ever write `data/` concurrently, and no key material ever lands in a log file.

<objective>
Deliver the protected HTTP surface of Phase 3 on top of the 03-01 execution core: `api/auth.py` (the X-API-Key dependency per D-10/D-11, reusing the Phase 1 `api.boot.read_token` chain verbatim), `api/actions.py` (the dependency-protected router with `POST /v1/actions/{kind}` → 202/404/409 and `GET /v1/jobs/{job_id}` → 200/404/503, the D-09 fixed-command map, and the job_id regex gate), the two-line `api/main.py` registration plus the single `jobs.reload_registry()` boot call (Pattern 4 placement, SEC-03 ordering untouched), and the two Wave-0 contract suites `tests/test_auth.py` (SEC-01) and `tests/test_actions.py` (ACT-01/02/03). This closes the phase's success criteria SC1/SC2/SC4 in-suite; SC5's registry half is 03-01 and its real-machine half is 03-04.

Purpose: the 03-01 core proved a job can run durably on this machine; this plan proves it can be *requested* safely — auth-before-everything, whitelist-only dispatch, atomic-claim 409s with a machine-readable running_job_id, and a byte-level guarantee that the key never appears in job logs, child environments, or responses.

Output: `api/auth.py`, `api/actions.py`, `api/main.py` (modified), `tests/test_auth.py`, `tests/test_actions.py`, green suite.
</objective>

## Flagged Assumptions (spec-less probe fallback — continuation)

Probe rows carried by this plan (ACT-01 and SEC-01; ACT-02/ACT-03 rows surfaced in 03-01):

- ACT-01 (`unclassified` probe — no scenario clause to honor): the phase's guarantee is a fixed whitelist, not a free-form surface: kind → KIND_CMDS lookup only, unknown kind → 404 before any side effect, request body never parsed/echoed/logged (D-09 zero parameters — Phase 4 SC4 will extend the parameter surface with a date whitelist and must remain backward compatible). - SEC-01 (`concurrency` probe — "If interrupted or run in parallel, what is guaranteed?"): auth is stateless and per-request — parallel requests each run their own `read_token` (env/file read) + `hmac.compare_digest` (pure, thread-safe, constant-time); there is no session, cache, or shared mutable auth state to corrupt. The token file is read fresh per request (a rotated token takes effect without restart when the env var is unset); [ASSUMED] file reads are consistent on NTFS for this access pattern. 401/403 paths perform no spawn and no registry write, so rejected requests cannot interfere with running jobs.
- [ASSUMED A4] Children never see or print the key (in-repo scripts read TUSHARE_TOKEN, never GOGO_API_TOKEN); defense in depth: the spawn env copy additionally pops GOGO_API_TOKEN, and the suite's grep audit asserts token absence in the job log bytes and in a child-dumped environment.
