# Plan 03-01 — Shared single-flight lock helper + durable job registry + spawn governance (ACT-02/ACT-03 core)

## Phase Goal (MVP framing, derived from the ROADMAP Goal line)

**As a** consumer of gogo's live operations (cloud panel, scheduled integrator, the user before market open), **I want to** POST a trigger for pipeline/morning-check/backtest-weights/health-check and get a 202 + job_id at once, poll the durable job to a terminal state, never double-run the same kind — even against the GUI's one-key refresh — and be refused with 401/403 whenever my X-API-Key is missing or wrong, **so that** I can drive gogo's core scripts remotely without touching the machine's console, freezing the API, or letting two runs of the same kind write `data/` concurrently.

> Note: the ROADMAP Phase 3 Goal line is prose, not user-story form; the story above is a word-level framing of that locked goal plus D-01..D-12 (user-signed in /gsd-discuss-phase). This plan delivers the durable-execution foundation the HTTP layer (03-02) and the GUI lock join (03-03) build on.

The four phase requirements were probed; all four rows came back `unresolved` (two `concurrency` probes, two `unclassified`). Per the fallback protocol these are surfaced, not dropped. Rows carried by this plan (the other two rows surface in 03-02):

- ACT-02 (concurrency — "If interrupted or run in parallel, what is guaranteed?"): the crash contract is deterministic-interrupted — a killed API leaves registry files in pending/running and the next boot's reload sweep rewrites them to the terminal `interrupted` state; every terminal job stays queryable (SC5). Residual edge, flagged: if the API is killed WITHOUT a tree-kill, the child may survive as an orphan and could still be writing when a same-kind job re-triggers after restart — the registry cannot distinguish this without PID adoption (v2 ACT-05 owns it); verification (03-04) therefore kills with taskkill /F /T to keep the scenario clean (RESEARCH Pitfall 3). Parallel different-kind runs are safe by construction: per-kind lock files, per-job registry files, pid-suffixed tmp names; prune races are ENOENT-tolerant.
- ACT-03 (concurrency — "If interrupted or run in parallel, what is guaranteed?"): the OS byte-range lock auto-releases when the holder process dies (probe V2, kill-tested) so no stale-lock cleanup protocol exists; same-process second acquisition is denied (probe V2) which serializes the API's own double-triggers at the OS level. [ASSUMED A3] fcntl.flock on macOS behaves equivalently (advisory, auto-release at process death) — Mac is GUI-manual only (no crontab lock, D-03), impact low, verify at Mac rollout.
- [ASSUMED A2] Starlette runs sync endpoints on a threadpool, so the future POST handler's bookkeeping never blocks the event loop; the SC3 /health-latency test in this plan pins the worker-thread half of the claim now and the live P95 check in 03-04 pins the endpoint half.
- [ASSUMED A1] A console-less spawn without CREATE_NO_WINDOW may flash a window under Task Scheduler context; the flag is harmless if unnecessary and is applied on nt (probe V4 verified flag value and rc propagation).
- [ASSUMED A6] Registry JSON written by this phase remains readable across restarts even if a future phase extends the schema — the field set is additive-tolerant and is a documented consumer surface.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Worker thread → child process | The API process hands an argv list + inherited env to a child python process; the child writes its own log file via the inherited handle |
| Child process → registry/log files | Child stdout/stderr bytes land in logs/api/jobs/{job_id}.log; job JSON is written only by the API process (atomic) |
| Filesystem → reload sweep | Registry files on disk are the crash-safe source of truth; boot sweeps rewrite them after a crash |
| Process boundary (GUI/other runner) | Another same-machine process may contend on data/locks/{kind}.lock — the OS arbitrates |
