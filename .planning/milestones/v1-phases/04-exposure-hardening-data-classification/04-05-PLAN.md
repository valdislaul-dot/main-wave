# Plan 04-05 — WR-01 boot fix (D-12): env-forced token for non-loopback binds + console warning, with test coverage

## User-story framing

**As a** user whose API could one day be pointed at 0.0.0.0 (by mistake or by a future LAN deployment), **I want to** the boot sequence to refuse exposure unless I have deliberately set GOGO_API_TOKEN in the environment — the auto-generated file must never count as intent — and to see a loud ASCII warning on the console whenever it does bind exposed — **so that** the privacy red line (2026-08-31) holds at the boot boundary, and the fail-closed check is proven by a test, not by documentation.

<objective>
Fix the P2-review WR-01 defect in the `api/main.py` SEC-03 branch: for non-loopback binds, require a non-empty `GOGO_API_TOKEN` environment variable as the ONLY satisfier (the `data/api_token.txt` file no longer passes — an auto-generated file is indistinguishable from a misconfiguration), refuse with the pinned ASCII error + `sys.exit(1)` before any token generation, and print an ASCII warning to stderr whenever a non-loopback bind proceeds with the env token (never echoing the value). Pin both new behaviors plus the unchanged loopback default in `tests/test_boot.py`.

Purpose: 04-CONTEXT adopts WR-01 (D-12: env 强制 token + 控制台警告) as the start-up hardening half of SEC-02 — today `has_token` passes on the file the service itself auto-generates, so a misconfigured `0.0.0.0` bind silently serves the LAN. SC2 explicitly requires the fail-closed boot check to be covered by a test, not just documentation; the pre-existing boot suite (cases 5/7) already covers refusal-without-token and env-satisfies — this plan adds the file-token-only refusal case (the actual WR-01 regression) and the warning pins.

Output: `api/main.py` (SEC-03 non-loopback branch only), `tests/test_boot.py` (new cases + minimal updates), green suite.
Decisions: D-22
</objective>
