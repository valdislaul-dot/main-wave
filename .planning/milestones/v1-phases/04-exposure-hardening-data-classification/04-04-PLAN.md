# Plan 04-04 — Trigger date whitelist (D-09 extension, SC4): API gate + single-source validator + script-side session-date acceptance

## User-story framing

**As a** consumer or scheduled integrator triggering the pipeline over HTTP, **I want to** pass an optional date in exactly the documented formats and have it reach the script as a plain argument-list token — while every other shape of input is refused before anything spawns — **so that** my date never becomes a shell-injection surface and the script can never be made to label a live run under a wrong session date.

<objective>
Deliver the SC4 date-parameter surface end-to-end: `api/actions.py` gains the optional `date` query param (whitelist + calendar validation via the new single-source pure module `scripts/daily/date_args.py`, 422s speaking the frozen envelope codes, single-token `--date=YYYY-MM-DD` appended after the fixed D-09 args for pipeline/morning-check only, zero-param kinds unchanged), `scripts/daily/run_pipeline.py` and `scripts/daily/morning_check.py` gain acceptance + a fail-loud session-date gate (refusal exit 2 before any capture/write/network when the date is not the local session date), with the argv-delivery pins in `tests/test_actions.py` and the pure-helper matrix in `tests/test_date_args.py`.

Purpose: SC4 requires whitelisted date params that reach scripts as argument lists with injection structurally impossible; 04-CONTEXT extends the D-09 surface for pipeline/morning-check only. The PATTERNS caution (a token the scripts never parse is inert; full historical re-run semantics cascade into every step module) is resolved by a documented planner decision: scripts validate and enforce session-date equality — the fail-loud option — so the parameter is real, provable, and cannot corrupt archives, while richer historical semantics stay open as a future user-signed extension on the same wire shape.

Output: `api/actions.py` (date param), `scripts/daily/date_args.py`, script-side gates in the two CLIs, `tests/test_actions.py` date pins, `tests/test_date_args.py`, green suite.
Decisions: D-26, D-27, D-28
</objective>

## Flagged Assumptions (spec-less probe fallback — continuation)

- STA-02/SEC-02 (`unclassified` probes): the date surface's user-signed contract is the whitelist formats + arg-list delivery + 422 on invalid format + zero-param kinds unchanged (04-CONTEXT 触发 date 参数面). The script-side *semantics* beyond acceptance are NOT user-specified (PATTERNS line 183) — planner decision executed here: a resolved date must equal the local session date (date.today()); anything else exits 2 before the first side effect with a clear ASCII message. Rationale: live captures always represent the current session, so labeling them under another date is data corruption (this project's data-integrity discipline treats that as serious), and historical replay semantics would cascade into every step module (each computes datetime.now() internally) — out of scope until the user defines them. The refusal is loud, the default path is byte-identical to pre-Phase-4 behavior, and the API never produces a failed job from a past date without the script's refusal message explaining why.
- [ASSUMED] The API appends the single token `--date=YYYY-MM-DD` (CONTEXT literal) and the scripts additionally accept the space-separated `--date <date>` form to stay consistent with the in-repo CLI idiom (data_health_check.py:102-110, review_recommendations.py) for manual users — both forms validated by the same resolver.
- [ASSUMED] The subprocess refusal pins (invalid/past date → exit 2) are safe in the offline suite because the gate precedes every network call and file write in both scripts; their module imports (run_pipeline pulls update_data etc.) perform no network and no writes at import time — if import-time side effects ever appear, the pin suite fails loudly and the executor isolates the import (never weakens the pin).
- [ASSUMED] Date resolution uses the machine's local date (date.today()) exactly like the scripts' existing datetime.now() session labeling — consistent by construction.
