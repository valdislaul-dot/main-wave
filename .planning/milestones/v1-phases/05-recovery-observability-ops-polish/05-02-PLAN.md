# Plan 05-02 — Bounded disk footprint: PRUNE_CAP 500→20 + api/log_housekeep.py rotation primitives + M-A boot dance in main() (OPS-03 SC2)

## User-story framing

**As an** operator leaving the service running for weeks, **I want to** never think about log files — each boot trims the job registry to the newest 20 pairs and re-opens a console.log that rotates at 5MB into a single console.log.1 history — **so that** the disk footprint stays bounded with zero manual cleanup and zero dependence on Windows logrotate.

<objective>
Land OPS-03 SC2 on the machine-verified Windows constraint: D-33's registry cap 500→20 at api/jobs.py:26 with the rewritten cap test, the D-34 pure-function api/log_housekeep.py module (rotate_console_log / repoint_std_streams / prune_job_logs primitives, 5MB one-generation rotation, call-time PRUNE_CAP default — no duplicate constant), and the M-A boot dance inserted in main() between jobs.reload_registry() (L103) and the lazy uvicorn import (L105): repoint → rotate → repoint → prune. The dance exists because the inherited cmd `>>` handle lacks FILE_SHARE_DELETE (machine-verified 2026-09-04): rename only succeeds after the first repoint releases the handle, and the second repoint lands the streams on the fresh file. Rotation failure is an ASCII WARNING at most — boot never blocks (SEC-03 discipline untouched).

Purpose: bounded disk footprint through weeks of continuous running (OPS-03 SC2). The registry cap was promised since Phase 3 — this plan lands it with a deterministic suite; live proof is deferred to the 05-04 real-machine gate (03-04 adapt-and-record precedent).

Output: cap 20 registry behavior + suite, api/log_housekeep.py + its suite, the main() dance + test_boot.py patch updates, green boot/jobs/housekeep suites.
Decisions: D-32, D-33, D-34 (discretion exercised: constants in log_housekeep/jobs.py (per 05-CONTEXT 工程常量不需配置化); rotation = boot size-check + one-generation .1 overwrite verbatim D-32; prune_job_logs default cap resolves api.jobs.PRUNE_CAP at call time — single source; repoint exposes no wrapper objects)
</objective>

## Flagged Assumptions (spec-less probe fallback — OPS-03 row unresolved, surfaced explicitly)

- [ASSUMED] The two-repoint ordering is required: (1) repoint_std_streams() releases the inherited no-delete-share handle (dup2 replacement closes it out of fds 1/2), (2) rotate_console_log()'s os.replace then succeeds, (3) repoint_std_streams() again opens/creates the fresh console.log so subsequent uvicorn stderr lands in the new file. A rotate-only or repoint-rotate sequence leaves streams attached to the renamed inode. The primitives are individually pure and unit-tested; the ordering's live proof is the 05-04 real-machine gate — if the real cmd semantics differ (e.g. sharing flags), adapt in 05-04 with the 03-04 adapt-and-record precedent and record the delta.
- [ASSUMED] When console.log is ≤ 5MB the dance still executes both repoints (uniform boot path, no branch) — reopening the same file fresh is harmless and sidesteps truncate-vs-append semantics entirely.
- [ASSUMED] The rewritten cap test seed (25 terminal + 3 inflight) exercises a boundary where the pre-change cap (500) would keep everything — the test provably fails on the old constant, so the cap change is the only way green.
