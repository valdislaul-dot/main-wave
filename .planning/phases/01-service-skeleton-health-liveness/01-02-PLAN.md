# Plan 01-02 — Windows autostart: run_api.bat + Task Scheduler registration (gogo-api)

## Phase Goal (MVP framing, derived from the ROADMAP Goal line)

**As a** Windows operator of the gogo machine, **I want to** start the service with one local command and have it come back by itself after a reboot through a registered Task Scheduler task, **so that** the /health probe stays green without any manual boot after restarts.

<objective>
Deliver the OPS-01 half of Phase 1 on top of Plan 01-01's api package: a repo-root `run_api.bat` launcher (D-09, `%~dp0`-derived, no stale hardcoded path) and `scripts/daily/install_api_task.ps1` that registers an idempotent, convention-shaped Task Scheduler task named `gogo-api` (D-07: AtStartup + 5-minute random delay, StartWhenAvailable, RestartCount 3 / 10-min, MultipleInstances IgnoreNew, Interactive/Limited principal for the current user, never SYSTEM). The plan ends by starting the registered task and probing the live service on the D-08 contract port; the real-reboot confirmation is the end-of-phase human check.

Purpose: The resident-service promise of the milestone — "auto-starts after reboot" (ROADMAP SC2) — is a Windows-OS capability that pytest cannot assert; it is delivered here through the repo's own registration convention and verified live on this machine.

Scope guard per D-10: this phase delivers Windows autostart only. The service code must stay Mac-runnable — api/main.py imports only path constants from scripts/daily/config.py (which auto-detects PROJECT_ROOT on both ends) and adds no Windows-only import — but the launchd plist is deferred to Phase 5 and no part of it is built here.

Output: `run_api.bat`, `scripts/daily/install_api_task.ps1`, one registered task `gogo-api`, and a running service reachable at 127.0.0.1:8000/health.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Task Scheduler → run_api.bat → python | The scheduled task executes a bat file from the repo at every startup; anything that can alter that bat (or the repo path it resolves) gains code execution as the interactive user at boot |
| Installer execution context | install_api_task.ps1 mutates the machine's task store; its path derivation (not its content) decides which bat the task runs — a stale path would register a launcher that no longer exists or points elsewhere |
| Local filesystem → registered task | logs/api/console.log is the task's only output channel; the token file data/api_token.txt sits in the same repo tree the task launches from |
