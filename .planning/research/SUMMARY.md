# Project Research Summary

**Project:** gogo (主升浪) — FastAPI HTTP API service layer over the existing Python A-share trading system
**Domain:** Long-running HTTP service layer (health/status/trigger/auth) wrapping a JSON-file-backed, dual-machine (Win primary / Mac sync), zero-automated-test script pipeline (27.5k LOC, 116 .py files, all state in `data/` + `logs/` JSON)
**Researched:** 2026-09-02
**Confidence:** MEDIUM–HIGH (HIGH on repo-grounded and machine-verified facts; MEDIUM on external server semantics)

## Executive Summary

This is a **shell-boundary wrapper service**: an HTTP API that must NOT modify any of the 116 existing pipeline files, must NOT import pipeline modules, must NOT create a second data source, and must NOT write business state. Experts build this with exactly two stable contracts to the existing system: a **file boundary for reads** (read existing `data/`/`logs/` JSON verbatim, surface freshness, never synthesize or "improve" data — 数据引用纪律) and a **process boundary for triggers** (spawn existing CLI scripts `run_pipeline.py`/`morning_check.py`/`backtest_v4.py`/`data_health_check.py` via subprocess with an argv/exit-code contract, exactly like the repo's own precedent `gui_dashboard.py:88`). All four research files converge on the same shape: one single uvicorn process (never `--workers`/`--reload` on Windows), FastAPI on the already-installed 0.115.x stack (no force-upgrade of the shared interpreter), stdlib-only for subprocess and auth (no Celery/Redis/JWT/ORM/Docker — each is documented overkill for a single-user, single-flight system), durable JSON job registry under `logs/api/`, per-kind single-flight locks, `202 + job_id + polling` triggers, X-API-Key default-deny on action routes, and default bind `127.0.0.1` with a fail-closed boot check. Target structure: new sibling package `scripts/api/` (config/main/security/state/runner/jobs + routers), writing ONLY under `logs/api/`.

The real risks are not HTTP design — they are collisions between a long-running server process and a batch system never built to be read concurrently. Research surfaced eight critical pitfalls, several proven by file:line code evidence: **(1)** most state JSON writes are non-atomic (`open(f,'w')` direct writes; only `zt_pool_state.json` and auction daily snapshots use tmp+`os.replace`) so a read can catch a half-written file; **(2)** on Windows a concurrent reader's open handle makes the writer's `os.replace` throw WinError 5/32 — and the repo's 119-place broad-`except` culture silently swallows that failure (the exact accident class behind the 7-day 赚钱效应恒0 incident); **(3)** no cross-process lock exists, so API-trigger + GUI one-key refresh (+ a possibly-defunct 15:30 scheduled task whose `auto_start.bat` hardcodes an old BASE path) can double-run a pipeline and corrupt same-day, non-regenerable data; **(4)** synchronous subprocess calls in async handlers freeze the entire event loop (all requests including /health); **(5)** auth/bind misconfiguration would expose the most sensitive local-only data (持仓/账本/候选 — kept off-cloud since 2026-08-31) plus remote code execution, on a repo already suspected public. Mitigations are structural and cheap if applied at the right phase: defensive read helper with retry + stale-cache fallback, lock files with PID liveness probes returning 409, one dedicated runner thread per spawn, loopback default + API-key enforcement, and the hard rule that **GET endpoints never make network calls** and **/health never 503s on data age** (data is stale by design on nights/weekends/holidays).

Build order follows dependency analysis: skeleton + `/health` first (zero risk to the system, satisfies the PROJECT.md Active requirement), read-only state passthrough second (delivers the read-API value, still zero pipeline risk), then the trigger runner with job registry + locks + auth enforcement (the Windows-subprocess risk concentration, isolated so its failure cannot take down what phase 2 delivered), then exposure hardening/data classification, and finally recovery/ops polish. Two cross-file design conflicts (response envelope vs raw-passthrough + freshness headers; asyncio subprocess vs thread+Popen runner) and three user sign-off gates under the project's 定稿机制 (PROJECT.md wording revisions for auth-by-data-classification; writer-side write atomicization which touches existing pipeline modules; whether GUI one-key refresh joins the same lock) must be settled in requirements before phases 2–3 are built.

### Recommended Stack

FastAPI on the **installed baseline** `fastapi>=0.115.14` (0.115.14 machine-verified 2026-09-02 on Python 3.13.1 with starlette 0.46.2/pydantic 2.13.4/uvicorn 0.51.0/httpx 0.25.2 — smoke-tested /health + APIKeyHeader 401/200 + TestClient). Do **not** force-upgrade past what the shared interpreter's ecosystem pins tolerate; latest (fastapi 0.141.1 / uvicorn 0.52.4) is only for the clean Mac side. Plain `uvicorn` (never `[standard]`: uvloop is Unix-only; no python-dotenv). **One single process, no `--workers`** — Windows multiprocessing spawn re-imports the app module (deadlock reports) and reload/workers force SelectorEventLoop which breaks asyncio subprocess; single process also keeps the in-memory job registry coherent. Pydantic v2 only for thin response models; **never** SQLAlchemy/SQLite/ORM — the JSON files ARE the database (不引入第二数据源 is a hard project rule). Auth with zero new deps: `fastapi.security.APIKeyHeader(name="X-API-Key")` + `secrets.compare_digest`, key from env `GOGO_API_TOKEN` then untracked `data/api_token.txt` (exact pattern of the existing Tushare token file). Auto-start: Windows Task Scheduler first (`python -m uvicorn api.main:app --host 127.0.0.1 --port 8001`, existing `install_scheduled_task.ps1` convention), NSSM only if headless/SLA demands. Dev tooling: `pytest` + TestClient (repo has zero tests; the API layer is the natural first seed), no venv isolation (subprocess triggers spawn `sys.executable` and need the pipeline's deps — venv only with `--system-site-packages` if a conflict appears).

**Core technologies:**
- Python 3.13.1 (machine): whole system already runs on it; FastAPI requires >=3.10
- FastAPI >=0.115.14: async-native HTTP + built-in OpenAPI `/docs`; 0.115.x fully sufficient for health/status/trigger
- uvicorn >=0.51.0 single process: the standard ASGI server; never `--workers`/`--reload` in production on Windows
- Pydantic v2 2.13.4: thin typed response schemas only — no re-architecture of state into a DB
- stdlib only for the load-bearing parts: subprocess (via runner), `secrets`/`hmac` compare, `json`, `time`, `sys`
- pytest 9.1.1 (dev): first automated tests in the repo, pure-endpoint TestClient over fixture JSON

### Expected Features

**Must have (table stakes, P1):**
- `GET /health` liveness — `{"status":"ok","uptime_seconds":N}`, always 200, zero deps, out of auth, `include_in_schema=False` (PROJECT.md Active requirement)
- **Staleness never 503s /health** — the single most important domain rule; data age is a payload concern, service health is a file-servability concern (night/weekend/holiday staleness is normal)
- Read-only status endpoints over existing JSON: market_state (temperature inputs) / auction_state / zt_pool_state, surfaced with as-of date + per-source freshness metadata
- X-API-Key auth on every operation-trigger endpoint (env-first, gitignored-file fallback, fail-fast at startup if missing, 401 missing/403 wrong)
- Triggers return immediately: `POST` → job record + spawn → `202 {job_id, status:"accepted"}`; `GET /jobs/{job_id}` polls pending/running/succeeded/failed — never a synchronous long request, never `subprocess.run()` inside an `async def` handler
- Triggers launch the EXISTING scripts only — no endpoint may write portfolio/candidates JSON itself (定稿机制: no second writer)

**Should have (differentiators):**
- Readiness probing the real served path: stat the exact JSONs each endpoint serves (existence + readability, cached) — kills the "probe green, app broken" pattern; `/health/ready` split so liveness stays bare
- Single-flight guard: in-process lock + advisory lock file with PID + 409 `{"running_job_id":...}` on overlap (also coordinates with the scheduled task where possible)
- Durable file-backed job registry (`logs/api/jobs/*.json`): survives API restart, re-attachable, startup reload marks running→interrupted, orphan detection via recorded PID
- Portfolio/temperature endpoints behind the SAME auth when bind ≠ 127.0.0.1 — account data is the most sensitive thing in this repo; "read-only = open" is the wrong default
- Pipeline digest endpoint aggregating data_health_check's 8-item report + warning fields (P2); auth-gated `GET /health/details` for humans (P2)

**Defer (v1.x / v2+):**
- Job cancellation (`taskkill /T /F` tree kill) — only if a runaway run actually happens (single-flight already prevents the worst case)
- ETag/304 conditional GETs, per-client rate limiting, orphan-adoption polish — trigger only when polling volume or an off-localhost deployment materializes
- Anti-features rejected outright: Celery/Redis/RQ, WebSocket push, webhooks, direct state-mutation endpoints (PUT/PATCH CRUD), JWT/OAuth2/user management, health internals on the public probe, and any GET endpoint that refreshes data by scraping (data-source-ban risk, 竞价 60s SLA)

### Architecture Approach

The architecture is a **Shell-Boundary Wrapper** (壳边界封装) with five core patterns: (1) the service and `scripts/daily/` share zero imports — contract is JSON file shape + CLI argv/exit-code; pipeline modules are "flat no-package layout + sys.path boilerplate + top-level side effects + lazy imports" so importing them couples the API to 27.5k LOC of untested code; (2) triggers are `202 + job_id + polling` with a durable JSON job registry — FastAPI BackgroundTasks is same-process fire-and-forget (lost on restart), Celery is overkill; (3) per-kind single-flight locks (in-process + portalocker/msvcrt-style advisory file lock, auto-released on process death) so API-triggered runs never double-run against each other; (4) freshness-proxying reads — response body IS the raw state file (drop-in compatible, zero consumer adaptation) with freshness in response headers `X-Data-Mtime`/`X-Data-Age-S`; (5) Windows subprocess governance — dedicated **thread** runner with `Popen` + `CREATE_NO_WINDOW`, `taskkill /F /T` tree kill for cancel/timeout, `PYTHONIOENCODING=utf-8` + `errors="replace"` (GBK hazard), never asyncio subprocess (Proactor terminate-hang history bpo-37381; Selector under reload/workers raises NotImplementedError).

**Major components (new sibling package `scripts/api/`, never inside `scripts/daily/`):**
1. `config.py` — self-locating BASE/DATA_DIR/LOG_DIR (up-traversal from `__file__`, independent of `scripts/daily`'s copy), env-first port/bind/key; reuse the daily `config.py` conventions, don't duplicate path logic
2. `main.py` — app factory + lifespan (startup job-registry reload, orphan marking); uvicorn target, `__main__` run
3. `routers/` — `health.py` (liveness), `state_routes.py` (GET /v1/state/* passthrough), `action_routes.py` (POST /v1/actions/{kind} → 202; GET/DELETE /v1/jobs/{id}); read/write split into two routers so default-deny auth is a router-level guarantee
4. `security.py` — X-API-Key dependency (constant-time compare, default-deny on action routes)
5. `services/state_reader.py` — read JSON + stat mtime, fast open→load→close, no pure-TTL caching (mtime-keyed if ever cached); must not hold handles (Windows os.replace sharing semantics)
6. `services/runner.py` — kind→argv registry dict + dedicated thread Popen/wait + per-kind single-flight + taskkill cancel; stdout to `logs/api/`
7. `services/jobs.py` — job records (uuid/kind/status/exit_code/times/log path), in-memory + atomic JSON persistence in `logs/api/jobs/`

Data flow is a one-directional loop: existing scripts write `data/`+`logs/` as they always have → API reads and proxies freshness → consumers see refreshed state after a run completes. API writes only to `logs/api/` (gitignored, out of sync_cloud whitelist, no churn to the bloated repo). Action-kind registry is one dict — new script = one new line. Scale: current single-user localhost shape needs zero caching and 1 worker; even dozens of polling consumers only need mtime-keyed cache; process-external queues only at 100+ concurrency or cross-machine triggers (never before). Read endpoints time-sensitive to 竞价 window semantics (9:15–9:35, snapshot <3min reuse) must NOT re-implement time rules — scripts own those guards; the API proxies only (avoids double-rule drift).

### Critical Pitfalls

1. **API reads half-written JSON (non-atomic writes)** — code evidence: only `data/zt_pool_state.json` (zt_pool.py:77-78) and `data/auction/YYYY-MM-DD.json` (auction_pool.py:341-342) use tmp+`os.replace`; `portfolio.json`, `trading_journal.json`, `market_state.json`, `auction_state.json`, `candidates_*.json` (multi-MB, widest write window), `zt_pool_exit_log.json` are direct `open(f,'w')` writes. The batch system's "write then read, single process" implicit contract is broken by a resident API. *Avoid:* mandatory single defensive `read_json` helper (read-once-close, JSONDecodeError short retry 1–2× 20–100ms, fallback to last-good TTL cache with `stale:true` flag — never a bare 500). Writer-side atomicization touches pipeline modules → **user decision gate** (see Gaps).
2. **Windows file sharing vs `os.replace` + silent-swallow culture** — CPython opens without FILE_SHARE_DELETE, so a reader holding a handle makes the WRITER's `os.replace` fail (WinError 5/32, indistinguishable errno 13); the repo's 119 broad `except` sites (incl. two bare `except: pass`) swallow it silently — the 2026-09-01 赚钱效应恒0 7-day accident class. *Avoid:* bounded PermissionError retry in any write helper with explicit failure marking (never swallow); readers open→load→close fast; no FileResponse/streaming of these files; Win+Mac concurrent read/write smoke in tests.
3. **Unlocked concurrent pipeline runs** — ARCHITECTURE.md states plainly: "无跨进程锁，并发运行两个流水线会竞争读写同一 state JSON". API triggers + GUI one-key refresh (gui_dashboard.py:88, currently unlocked) + the 15:30 scheduled task (auto_start.bat hardcodes old BASE path — likely defunct, verify) = corrupted same-day data, duplicate scraping hitting rate-limited sources (1s+ intervals, ban history), and Step9 `sync_cloud` git commit conflicts (`.git/index.lock`). *Avoid:* single-flight lock is a trigger-phase acceptance gate — lock file with PID + start time, Windows PID probe via `tasklist /FI "PID eq n"` (`os.kill(pid,0)` unreliable), mtime timeout fallback (>90min full / >20min `--fast`), 409 with running job_id; trigger default `--fast` (skips Step9 git push) removes the git concurrency surface.
4. **Synchronous subprocess blocks the event loop** — `subprocess.run` (or any sync block, even wrapped in BackgroundTasks/`asyncio.create_task`) inside async handlers freezes ALL requests including /health; `await proc.wait()` without consuming stdout/stderr deadlocks at the 64KB pipe buffer. *Avoid:* 202+job_id pattern with background execution through a runner (thread + Popen) — or create_subprocess_exec + communicate/DEVNULL; ordinary `def` endpoints for sync work (threadpool); never `cmd /c`/shell=True; gui_dashboard's `timeout=180` kill pattern is a documented anti-example (kills `--fast` mid-write → next-morning half-file reads).
5. **Auth/bind misconfiguration** — 0.0.0.0 without token exposes 持仓/账本/候选 (2026-08-31 privacy line: local-only, more sensitive than anything on GitHub) + trigger RCE, on a repo suspected public (anonymous HTTP 200 in CONCERNS.md); CORS `["*"]`+credentials is a FastAPI-documented forbidden combo; token in URL/logs, token files in git/sync whitelist are real leaks (plaintext token files already precedented in `data/`). *Avoid:* default bind 127.0.0.1; fail-closed boot (non-loopback bind without token = refuse to start, not warn); auth by **data classification** — market/temperature public-safe, 持仓/账本/候选/trigger all token (revise PROJECT.md wording); token in header only, constant-time compare, never logged; no CORS middleware unless a browser consumer exists (then explicit origin list); param whitelist regex + arg-list spawn (a date param can monkey-patch datetime and rewrite history).

## Implications for Roadmap

Suggested structure: **5 phases** (mapping to the research files' convergent orderings: ARCHITECTURE A–E; PITFALLS P1–P4 split at hardening). Each phase is independently verifiable and rollback-safe; phases 1–2 carry zero risk to the existing system, phase 3 concentrates all Windows-subprocess risk behind the phase-2 read-only deliverable, auth scaffold lands early (PITFALLS: "安全后置是最大返工源") with enforcement wired at the first action route.

**Delivers:** `scripts/api/` package: config.py (self-locating BASE, env-first GOGO_API_PORT/GOGO_API_TOKEN, bind default 127.0.0.1), main.py app factory, `GET /health` pure in-memory (`{"status":"ok","uptime_seconds":N}`, 200 always, no disk, no auth, `include_in_schema=False`), run_api.bat/.sh, Task Scheduler registration on Win (proven `install_scheduled_task.ps1` convention; NSSM documented upgrade path), launchd plist on Mac, pytest seed (TestClient health test). **Auth scaffold in this phase:** token resolution (env → `data/api_token.txt`), fail-fast boot check (missing token + non-loopback bind = refuse start), security.py dependency skeleton.
**Uses (STACK):** fastapi>=0.115.14, uvicorn>=0.51.0 single process, Python 3.13.1; stdlib only beyond that.
**Avoids (PITFALLS):** /health–freshness coupling (moderate trap — health never reads state files or 503s on age), auth-postponement rework (Pitfall 5 — mechanism P1-就位).
**Research flag:** none — standard patterns, stack machine-verified, Task Scheduler vs NSSM already researched (MEDIUM).

### Phase 5: Recovery, Observability, Ops Polish
**Rationale:** Last — everything before runs fine with manual startup; this hardens the resident-service reality (restarts, crashes, disk growth, debugging from afar).

**Research flag:** none — standard ops patterns.

### Phase Ordering Rationale
- **Dependency-driven:** state-file registry (P2) precedes any endpoint that reports freshness; runner/jobs/locks (P3) all depend on P2's registry and P1's app; security enforcement must exist before the first action route is reachable (P3), while its config scaffold ships in P1 to kill the "auth postponed = biggest rework source" trap.
- **Risk isolation:** phases 1–2 never touch subprocess/Windows-process semantics → zero pipeline risk and independently shippable read value; all Windows subprocess risk concentrates in P3, verifiable in isolation ("若 runner 出问题，只读 API 仍可交付").
- **User-gate batching:** every item that touches existing pipeline modules or PROJECT.md constraints (writer atomicization H, GUI lock J, PROJECT.md security/constraint wording) is batched into the two decision points (before P2 contract coding, before P3 coding) so the user confirms once per mechanism-change cluster per 定稿机制.
- **Cross-file conflicts resolved in requirements:** A (response contract), B (subprocess mechanism), C (auth timing — scaffold P1 / enforce P3 / full policy P4), D (single-flight in P3, NOT deferred to v1.x as FEATURES.md suggested — PITFALLS/ARCHITECTURE evidence wins), E (/health payload purity), F (X-API-Key header per machine verification; hygiene rules non-negotiable), G (path scheme: ARCHITECTURE's `/v1/state/*`, `/v1/actions/{kind}`, `/v1/jobs/{id}` registry design — extensible kind→argv table).

### Gaps to Address

- **Decision A — response contract conflict:** FEATURES.md mandates a `{"data":…,"meta":{freshness}}` envelope (P1) while ARCHITECTURE.md Pattern 4 explicitly rejects body envelopes in favor of raw-file bodies + freshness headers. **Recommendation:** raw passthrough + `X-Data-Mtime`/`X-Data-Age-S` headers for file-backed `/v1/state/*` endpoints (drop-in compatibility with file schemas consumers already parse is the reuse value); data/meta envelope reserved for synthesized endpoints (jobs, digest) that have no file schema.
